# 小米 mimo 翻译耗时分析

实测日期：2026-09-17。对象为 Hacker News 列表第二页的 30 条标题，共 1602 个原文字符。加载当前 dist，使用用户「小米mimo」配置的隔离副本：mimo-v2.5，并发 4，自动重试 3 次，简体中文。用户浏览器配置和业务代码未修改；包含配置副本的临时浏览器目录已删除。

## 结果

| 场景 | 首条译文提交 DOM | 整页观察结果 | HTTP 尝试 |
| --- | --- | --- | --- |
| 原配置，无本地缓存 | 10.797 秒 | 89.435 秒时仍未完成：8 成功、8 失败、14 未完成 | 已发出 14 次 |
| 相同配置和正文，无本地缓存，仅临时注入 thinking.type=disabled | 4.125 秒 | 17.415 秒，30 成功、0 失败 | 8 次 |
| 全部命中本地缓存 | 11.5 毫秒 | 27.1 毫秒，30 成功 | 0 次 |

原配置记录的是观察截点，不是整页完成时间；之后停止测试。每组为单次样本，服务延迟及服务端 prompt cache 会影响数值。前两组均清空隔离环境的本地译文缓存，模型、API、Prompt、并发和重试次数保持一致。DOM 随译文插入会改变当前视窗分组，不能把时差当作所有网页固定的提速倍率。

## 主要瓶颈

1. **默认思考模式。** 当前请求只有 model、stream、messages，没有 thinking 参数。小米官方文档规定 mimo-v2.5 默认 thinking.type=enabled。实测四个初始请求均 HTTP 200，约 0.59–2.03 秒获得响应头；两个成功请求到约 9.54 / 12.73 秒才出现正文 content。另两个只持续产生 reasoning_content，20 秒内没有译文 content。只统计了思考字符数，未保存其文本。
2. **思考耗时碰上超时重试。** 前台请求每次只有 20 秒；配置的 3 次重试意味着最多 4 次尝试。两个批次持续超时，约 4×20+3×0.4=81.2 秒后失败。原配置已结束的 10 次尝试中，2 次返回译文，另 8 次耗时约 20 秒；所有已观察到的响应头均为 200，没有观察到 429。
3. **有序渲染和屏外派发门槛放大等待。** 非缓存的完整结果仍要等同一 lane 中前面的段落；本次最长 orderedWait 达 67.838 秒。缓存命中已绕过该门槛。当前视窗未全部结束时，屏外请求不能使用空出的并发名额；原配置的下一组请求到约 81 秒才开始。关闭思考后仍有 5.2 秒的最大顺序等待。

原配置阶段统计：DOM 发现累计 17.6 毫秒，配置预检 10.6 毫秒，缓存查询累计 116.3 毫秒，后台请求队列等待累计 16.5 毫秒、最大 1.9 毫秒，DOM 渲染累计 6.4 毫秒。这些并发或重叠阶段不能相加当作整页耗时。这里的 queue 是后台请求准入等待，不包括内容调度器尚未派发的工作。

## 优化顺序

优先为此配置显式关闭 thinking，先解决长时间思考触发反复超时的问题。随后考虑让已完成网络段落直接渲染，并在可视任务优先的前提下允许屏外任务填补空闲名额。单纯提高并发或增加重试次数无法消除上述等待链。本次只验证性能和完整结果返回，未系统评估关闭思考后的译文质量。

## 证据

- measurements.json：各阶段和请求统计，仅保留耗时、字符数、usage 等诊断字段，不含 Key、Prompt、原文、译文或思考文本。
- src/shared/openai-client.ts：请求体及自动重试循环。
- src/background/service-worker.ts：visible/readAhead/background 分别 20/30/60 秒的请求限制。
- src/content/controller.ts：flushOrderedRenderLane 和 canDispatchBackground。
- src/content/translation-scheduler.ts：dispatch 的屏外任务门槛。
- 官方默认思考及关闭参数：https://mimo.mi.com/docs/en-US/api/chat/openai-api
